# Plan 019: ECS-Lite Architecture for Game-Level State Management

## Executive Summary

This plan proposes migrating the scanner application to an Entity-Component-System (ECS) inspired architecture to support complex interactive features like dynamic tuner allocation, concurrent scans, priority-based resource management, and sophisticated UI state synchronization. The architecture is inspired by modern game engines but adapted for the specific needs of SDR scanning.

## Problem Statement

Current requirements exhibit game-level complexity:

1. **Dynamic resource allocation**: Tuners allocated based on priorities, availability, and constraints
2. **Interactive state changes**: User can interrupt scans to listen to stations, affecting resource allocation
3. **Multi-objective operations**: Multiple scans running concurrently with shared tuner pool
4. **Complex UI synchronization**: Spectrum display updates based on active station, scan progress, and discovered stations
5. **Per-resource configuration**: Each tuner has individual priorities and frequency constraints

The current architecture, while well-structured, is not optimized for this level of dynamic interaction. State is spread across:
- `ScannerState` (scanning/paused/listening modes)
- `Pool` (tuner allocation and availability)
- `TUI Model` (UI state and navigation)
- `ScanContext` (scanning progress and audio session)

This separation makes it difficult to implement features requiring coordination across these boundaries.

## Proposed Architecture: ECS-Lite

### Core Principles

**Entity-Component-System** without the overhead:
- **Entities**: Lightweight identifiers for tuners, scans, stations, audio sessions
- **Components**: Pure data structures representing different aspects of entity state
- **Systems**: Pure functions that operate on components to implement behavior
- **Update Loop**: Existing task scheduler serves as the game loop

**Key difference from full ECS**: We don't need Bevy's performance optimizations (cache-friendly memory layout, parallel system execution) because we have dozens of entities, not thousands. We adopt ECS principles for clarity and flexibility.

## System Design

### System 1: Device Discovery System

**Responsibility**: Handle device connect/disconnect events, update tuner entity states.

**Inputs**:
- Discovery events (DeviceAdded, DeviceRemoved)

**Outputs**:
- Creates/removes tuner entities
- Updates `DeviceComponent.connected` flags

**Logic**:
```rust
fn device_discovery_system(
    events: &[DiscoveryEvent],
    tuners: &mut EntityStore<TunerEntity>,
) {
    for event in events {
        match event {
            DiscoveryEvent::Added(device_meta) => {
                for channel in 0..device_meta.num_tuners {
                    let tuner = TunerEntity::new(
                        device_meta.device_id.clone(),
                        channel,
                        device_meta.capabilities.clone(),
                    );
                    tuners.insert(tuner);
                }
            }
            DiscoveryEvent::Removed(device_id) => {
                tuners.remove_by_device(device_id);
            }
        }
    }
}
```

**When to run**: After processing discovery events each tick.

### System 2: Tuner Allocation System

**Responsibility**: Allocate tuners to scans and audio sessions based on priorities and availability.

**Inputs**:
- Tuner entities with priorities, constraints, allocation state
- Scan entities requesting tuners
- Audio session entities requesting tuners

**Outputs**:
- Updates `AllocationComponent.state` and `allocated_to`
- Updates `ScanAllocationComponent.allocated_tuners`
- Updates `AudioAllocationComponent.tuner_id`

**Logic**:
```rust
fn tuner_allocation_system(
    tuners: &mut EntityStore<TunerEntity>,
    scans: &mut EntityStore<ScanEntity>,
    audio: &mut EntityStore<AudioSessionEntity>,
) {
    // Priority order: Audio (if high priority) > Scanning > Audio (if low priority)

    // Step 1: Handle audio sessions with high priority
    for session in audio.iter_mut().filter(|a| needs_tuner(a)) {
        if let Some(tuner_id) = find_best_tuner_for_audio(tuners, session, Priority::High) {
            allocate_tuner_to_audio(tuners, session, tuner_id);
        }
    }

    // Step 2: Handle scans
    for scan in scans.iter_mut().filter(|s| needs_more_tuners(s)) {
        while scan.allocation.allocated_tuners.len() < scan.allocation.requested_tuner_count {
            if let Some(tuner_id) = find_best_tuner_for_scan(tuners, scan) {
                allocate_tuner_to_scan(tuners, scan, tuner_id);
            } else {
                break;  // No more tuners available
            }
        }
    }

    // Step 3: Handle audio sessions with medium/low priority
    for session in audio.iter_mut().filter(|a| needs_tuner(a) && !has_tuner(a)) {
        if let Some(tuner_id) = find_best_tuner_for_audio(tuners, session, Priority::Medium) {
            allocate_tuner_to_audio(tuners, session, tuner_id);
        }
    }
}

fn find_best_tuner_for_audio(
    tuners: &EntityStore<TunerEntity>,
    session: &AudioSessionEntity,
    min_priority: Priority,
) -> Option<TunerId> {
    tuners
        .iter()
        .filter(|t| t.device.connected)
        .filter(|t| t.allocation.state == AllocationState::Available)
        .filter(|t| t.priorities.audio >= min_priority)
        .filter(|t| t.constraints.allows_frequency(session.tuning.frequency))
        .max_by_key(|t| t.priorities.audio)
        .map(|t| t.id.clone())
}

fn find_best_tuner_for_scan(
    tuners: &EntityStore<TunerEntity>,
    scan: &ScanEntity,
) -> Option<TunerId> {
    let next_freq = scan.config.windows[scan.progress.window_index];

    tuners
        .iter()
        .filter(|t| t.device.connected)
        .filter(|t| t.allocation.state == AllocationState::Available)
        .filter(|t| t.priorities.scanning != Priority::None)
        .filter(|t| t.constraints.allows_frequency(next_freq))
        .max_by_key(|t| t.priorities.scanning)
        .map(|t| t.id.clone())
}
```

**When to run**: After input handling, before scan processing.

### System 3: Scan Processing System

**Responsibility**: Advance scan progress using allocated tuners.

**Inputs**:
- Scan entities with allocated tuners
- Tuner entities with current allocation

**Outputs**:
- Updates `ProgressComponent.window_index`
- Updates `ProgressComponent.window_states`
- Creates station entities for discovered stations
- Updates `StatusComponent` on tuners

**Logic**:
```rust
fn scan_processing_system(
    scans: &mut EntityStore<ScanEntity>,
    tuners: &EntityStore<TunerEntity>,
    stations: &mut EntityStore<StationEntity>,
    pool: &Pool,
) {
    for scan in scans.iter_mut() {
        if scan.status.paused || scan.status.status != ScanStatus::Running {
            continue;
        }

        // Process next window if we have an available tuner
        if let Some(tuner_id) = scan.allocation.allocated_tuners.first() {
            let window_freq = scan.config.windows[scan.progress.window_index];

            // Process window using pool (existing logic)
            let discovered = process_window(pool, tuner_id, window_freq, &scan.config.config);

            // Create station entities for discoveries
            for signal in discovered {
                let station = StationEntity::from_signal(signal, scan.id, StationSource::CurrentScan);
                stations.insert(station);
            }

            // Advance progress
            scan.progress.window_index += 1;
            if scan.progress.window_index >= scan.progress.windows_to_process {
                scan.status.status = ScanStatus::Complete;
            }
        } else {
            // No tuner available - pause scan
            scan.status.paused = true;
            scan.status.paused_reason = Some(PauseReason::NoAvailableTuners);
        }
    }
}
```

**When to run**: After tuner allocation, each tick while scans are active.

### System 4: Audio Management System

**Responsibility**: Manage audio playback sessions.

**Inputs**:
- Audio session entities
- Tuner entities
- Station entities

**Outputs**:
- Updates audio session playback state
- Updates tuner status to Listening

**Logic**:
```rust
fn audio_management_system(
    audio: &mut EntityStore<AudioSessionEntity>,
    tuners: &EntityStore<TunerEntity>,
    stations: &EntityStore<StationEntity>,
) {
    for session in audio.iter_mut() {
        let tuner = tuners.get(&session.allocation.tuner_id);
        let station = stations.get(&session.tuning.station_id);

        if !tuner.device.connected {
            // Tuner disconnected - pause audio
            session.playback.session.pause();
            continue;
        }

        // Ensure tuner is tuned to correct frequency
        if tuner.status.current_frequency != Some(session.tuning.frequency) {
            tune_tuner(tuner, session.tuning.frequency);
        }

        // Update playback if needed
        session.playback.session.update();
    }
}
```

**When to run**: Each tick while audio sessions are active.

### System 5: Input Handling System

**Responsibility**: Process user input and create/modify entities accordingly.

**Inputs**:
- User input events (key presses, commands)
- Current entity state

**Outputs**:
- Creates new scan/audio entities
- Modifies scan status (pause/resume)
- Modifies tuner priorities/constraints
- Triggers tuner reallocation

**Logic**:
```rust
fn input_handling_system(
    input: &InputEvent,
    scans: &mut EntityStore<ScanEntity>,
    audio: &mut EntityStore<AudioSessionEntity>,
    tuners: &mut EntityStore<TunerEntity>,
    stations: &EntityStore<StationEntity>,
) {
    match input {
        InputEvent::SelectStation(station_id) => {
            // User pressed ENTER on a station
            let station = stations.get(station_id);

            // Create or update audio session
            if let Some(existing) = audio.iter_mut().next() {
                // Switch existing session to new station
                existing.tuning.station_id = *station_id;
                existing.tuning.frequency = station.info.frequency;
            } else {
                // Create new audio session
                let session = AudioSessionEntity::new(*station_id, station.info.frequency);
                audio.insert(session);
            }

            // Allocation system will handle tuner allocation on next tick
        }

        InputEvent::ConfigureTuner { tuner_id, priorities, constraints } => {
            // User configured tuner priorities/constraints
            if let Some(tuner) = tuners.get_mut(tuner_id) {
                tuner.priorities = priorities;
                tuner.constraints = constraints;
            }

            // Reallocation will happen on next tick
        }

        InputEvent::StartScan(config) => {
            // User started a new scan
            let scan = ScanEntity::new(config);
            scans.insert(scan);
        }

        InputEvent::PauseScan(scan_id) => {
            if let Some(scan) = scans.get_mut(scan_id) {
                scan.status.paused = true;
                scan.status.paused_reason = Some(PauseReason::UserRequested);
            }
        }

        InputEvent::ResumeScan(scan_id) => {
            if let Some(scan) = scans.get_mut(scan_id) {
                scan.status.paused = false;
                scan.status.paused_reason = None;
            }
        }
    }
}
```

**When to run**: First, at the beginning of each tick.

### System 6: UI Update System

**Responsibility**: Update TUI model based on current entity state.

**Inputs**:
- All entities (read-only query)

**Outputs**:
- Updates TUI Model

**Logic**:
```rust
fn ui_update_system(
    tuners: &EntityStore<TunerEntity>,
    scans: &EntityStore<ScanEntity>,
    stations: &EntityStore<StationEntity>,
    audio: &EntityStore<AudioSessionEntity>,
    tui_model: &mut Model,
) {
    // Update tuner display
    tui_model.tuners.clear();
    for tuner in tuners.iter() {
        tui_model.tuners.insert(tuner.id.clone(), TunerDisplayInfo {
            device_id: tuner.device.device_id.clone(),
            channel: tuner.device.channel_index,
            connected: tuner.device.connected,
            activity: tuner.status.activity,
            allocated: tuner.allocation.state == AllocationState::Allocated,
            frequency: tuner.status.current_frequency,
        });
    }

    // Update scan progress
    for scan in scans.iter() {
        tui_model.update_scan_progress(scan.id, &scan.progress, &scan.status);
    }

    // Update station list
    tui_model.discovered_stations.clear();
    for station in stations.iter().filter(|s| s.source.source == StationSource::CurrentScan) {
        tui_model.discovered_stations.push(station.into());
    }

    // Update spectrum display
    if let Some(session) = audio.iter().next() {
        tui_model.active_station = Some(session.tuning.station_id);
        tui_model.spectrum_center = session.tuning.frequency;

        // Highlight nearby stations
        tui_model.spectrum_stations = stations
            .iter()
            .filter(|s| is_nearby(s.info.frequency, session.tuning.frequency))
            .map(|s| (s.info.frequency, s.id == session.tuning.station_id))
            .collect();
    }
}
```

**When to run**: After all other systems, before rendering.

## Update Loop Integration

The existing task scheduler serves as our game loop. Each system runs in a specific order each tick:

```rust
// In main_thread/mod.rs or new coordinator module

struct WorldState {
    tuners: EntityStore<TunerEntity>,
    scans: EntityStore<ScanEntity>,
    stations: EntityStore<StationEntity>,
    audio: EntityStore<AudioSessionEntity>,
}

fn update_tick(
    world: &mut WorldState,
    input_events: Vec<InputEvent>,
    discovery_events: Vec<DiscoveryEvent>,
    tui_model: &mut Model,
    pool: &Pool,
) {
    // System execution order

    // 1. Handle discovery events
    device_discovery_system(&discovery_events, &mut world.tuners);

    // 2. Handle user input
    for event in input_events {
        input_handling_system(
            &event,
            &mut world.scans,
            &mut world.audio,
            &mut world.tuners,
            &world.stations,
        );
    }

    // 3. Allocate tuners based on priorities
    tuner_allocation_system(
        &mut world.tuners,
        &mut world.scans,
        &mut world.audio,
    );

    // 4. Process scans with allocated tuners
    scan_processing_system(
        &mut world.scans,
        &world.tuners,
        &mut world.stations,
        pool,
    );

    // 5. Manage audio playback
    audio_management_system(
        &mut world.audio,
        &world.tuners,
        &world.stations,
    );

    // 6. Update UI model
    ui_update_system(
        &world.tuners,
        &world.scans,
        &world.stations,
        &world.audio,
        tui_model,
    );
}
```

## Entity Store Implementation

Simple HashMap-based storage (not optimized like full ECS):

```rust
struct EntityStore<T> {
    entities: HashMap<T::Id, T>,
    next_id: u64,
}

impl<T: Entity> EntityStore<T> {
    fn insert(&mut self, entity: T) -> T::Id {
        let id = entity.id();
        self.entities.insert(id.clone(), entity);
        id
    }

    fn get(&self, id: &T::Id) -> Option<&T> {
        self.entities.get(id)
    }

    fn get_mut(&mut self, id: &T::Id) -> Option<&mut T> {
        self.entities.get_mut(id)
    }

    fn iter(&self) -> impl Iterator<Item = &T> {
        self.entities.values()
    }

    fn iter_mut(&mut self) -> impl Iterator<Item = &mut T> {
        self.entities.values_mut()
    }
}

trait Entity {
    type Id: Clone + Eq + Hash;
    fn id(&self) -> Self::Id;
}
```

- **Refactorable**: Change component structure without affecting unrelated systems

## Risks and Mitigations

### Risk: Over-engineering

**Mitigation**: Start with minimal ECS (Phase 1-2) and validate before expanding. If complexity doesn't justify benefits, stop migration.

### Risk: Performance regression

**Mitigation**: Profile each phase. Set performance budget. Use simple HashMap storage instead of optimized ECS memory layout.

### Risk: Migration complexity

**Mitigation**: Incremental migration with backward compatibility. Keep old code working until new code is validated.

### Risk: Learning curve

**Mitigation**: Extensive documentation and examples. Start with simple entities (tuners) before complex ones (scans).

## Alternatives Considered

### Alternative 1: Keep Current Architecture

Continue with `Pool`, `ScannerState`, `TUI Model` separation.

**Rejected because**: Implementing complex interactions requires coordinating state across these boundaries, leading to complex coupling and hard-to-trace bugs.

### Alternative 2: Full Bevy ECS

Use Bevy engine's full ECS implementation.

**Rejected because**: Massive dependency for limited benefit. We don't need Bevy's cache-friendly memory layout or parallel system execution for dozens of entities.

### Alternative 3: Event Sourcing

Record all state transitions as events, replay to reconstruct state.

**Rejected because**: Over-engineered for real-time interactive application. Event sourcing makes sense for persistence and audit trails, not for managing interactive state.
